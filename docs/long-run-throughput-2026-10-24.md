# 400 页扫描件 15 分钟：吞吐瓶颈分析与优化

分析对象：[运行 40083856282](https://github.com/ActiveInsighter/file-converter-ai/actions/runs/40083856282)
（提交 `b12eaef`）。源文件 723 MB、400 页扫描件；Gemini 3.5 Flash-Lite，66 个 Key，
并发 20，240 DPI PNG，`thinking_level=high`，`media_resolution=ultra_high`，
PaddleOCR 经中继。Runner 上的转换步骤 09:55:25 → 10:10:41，共 15 分 16 秒。

## 时间线（日志实测，UTC，t=0 为 09:55:26）

| 阶段 | 时间 | 说明 |
| --- | --- | --- |
| 下载 723 MB | 0 → 64 s | 单连接约 11 MB/s，期间 OCR、渲染、模型全部空闲 |
| 第一段 OCR | 64 → 150 s | 裁剪 + 上传 43 MB 到中继 28 s，百度处理 55 s；首个模型请求在 151 s，**模型空等 2.5 分钟** |
| 稳定阶段 | 150 → 600 s | 完成 316/400 页，约 0.72 页/s；每段首个模型请求都紧跟该段 OCR 完成后 1–3 秒 |
| **尾部** | 600 → 920 s | 最后一段 376–400 的中继提交被百度回 **HTTP 408**，整个中继被停用，改为 20–25 KB/s 的直接上传，拆成 3 页一段，每段提交 43–77 s，**约 5 分钟里模型几乎无事可做**，占总时长三分之一 |

## 瓶颈

1. **一次 HTTP 408 毁掉尾部（约 5 分钟）。** `_check` 只把 429/5xx 当作可重试；408 变成普通
   `RuntimeError`，被 `_submit_relay` 的 `except Exception` 捕获后调用 `_abandon_relay`：整个任务
   不再用中继，剩余分段全部走 20–25 KB/s 的上传。文件已在中继上，重试同一链接几乎肯定成功。
2. **OCR 是模型阶段的门槛，且每段 43 MB。** 日志里 15 个中继提交耗时 18–70 s（平均约 38 s），
   其中包含 43 MB 的上传，以及百度在提交请求里同步下载同样大小的文件。3 个任务并行，每个任务的周期
   ≈ 38 s 提交 + 50 s 处理，对应约 0.8 页/s，与模型阶段 0.72 页/s 几乎相同——两个阶段互相等待。
   裁剪和上传还发生在任务槽之内，占着 3 个名额中的一个。
3. **队头阻塞。** 页面按页码进入 20 个工作槽，每页在槽内等待自己的 OCR 草稿。301–325 段的 OCR
   用了 120 s，而 326–350、351–375 早已完成；20 个槽全被 301–320 页占着等草稿，已就绪的页面只能干等
   （约 40 s）。
4. **首批草稿太慢。** 第一个 OCR 任务就是 25 页，模型在 151 s 才开工。
5. **下载单连接。** 11 MB/s，64 s。
6. **模型并发 20 偏低。** 请求 p50 16.7 s、p95 25 s，429 为 0、503 仅 7 次，66 个 Key 的额度只用了很小一部分；
   并发 20 的理论上限约 1.2 页/s。OCR 提速之后，这会成为下一个瓶颈（工作流默认是 50，前端传了 20）。

## 改动

| 改动 | 针对 | 位置 |
| --- | --- | --- |
| HTTP 408/504 与无响应视为“百度没能及时拉取”：在**同一条已上传的链接**上重试，同一段连续两次失败才只把这一段改为上传；中继对其他段继续使用 | 1 | `paddle_ocr.py` `OcrFetchTimeout`、`_submit_relay` |
| 中继分段先把重型扫描页重编码为 150 DPI JPEG（本机实测 25 页 82 MB → 12.7 MB），在工作进程中做（线程实测无法并行：4 线程 16.6 s，串行 15.0 s，4 进程 5.5 s）；`CONVERTER_OCR_RELAY_DPI=0` 可保留原图 | 2 | `rasterise_segment`、`_cut`、`_rasterise` |
| 裁剪与上传在任务槽之外预备，最多提前 2 段，槽一空出直接提交链接 | 2 | `_take_job_slot`、`_stage_relay` |
| 前三段为 5/10/15 页，之后 25 页；完成时间错开 | 4 | `ramp_segments` |
| 按“OCR 草稿先就绪的页先处理”调度，渲染最多领先 `max(60, 3×并发)` 页 | 3 | `pipeline.ready_first`，`pdf2md.process_pages` |
| 源站支持 Range 且 ≥ 32 MB：8 连接并行下载 16 MB 分块；任何异常退回单连接；`If-Range` 检测下载中途变化 | 5 | `downloads.py` |

## 验证

* `python -m unittest discover -s tests`：201 项通过（改动前 182 项）；新增用例在改动前的代码上均失败。
* 并行下载：本地每连接限速 8 MB/s 的 Range 服务器，64 MB：单连接 8.2 s → 8 连接 2.1 s，内容 SHA-256 一致。
* 流水线模拟（OCR 阶段，实时 1:1）：结果见本文末尾“模拟结果”一节。

## 没有改动的

* 模型阶段的 `thinking_level`、`media_resolution`、DPI、PNG：这些影响转写质量，需要用真实 API 做质量对比才能调整，
  本次没有真实 Key 与 OCR 令牌，未改默认值。若质量允许，降低 `thinking_level` 与改用 JPEG 是下一个最有潜力的点
  （单次请求 p50 16.7 s）。
* 前端 `concurrency`：见下一节。

## 建议的运行参数

OCR 提速之后，并发 20 会成为模型阶段的上限（≈ 20 ÷ 16.7 s ≈ 1.2 页/s）。66 个 Key 在日志中 429 为 0，
建议下次把 `concurrency` 提到 40–50（工作流默认 50）。

### 失控输出

三份默认提示词的运行里都出现了单页数万字符的重复输出：133 有 2 页（约 9 千字符）、134 有 4 页
（3.7–10.6 万字符，`&nbsp;`/整行表格重复）、135 有 2 页（含 7.3 万字符的第 379 页）；旧版自定义提示词那次有 1 页（2.4 万）。
它与 150 DPI 无关（原图那次同样出现）。`pdf2md.validate_markdown_output` 现在把“单页超过 3 万字符”或
“同一短片段连续重复 400 次以上”当作不可用输出，页面重试，重试用尽退回 OCR 草稿；用这四次运行约 1600 页检查，
只命中明显退化的页，表格缩进里常见的 40–120 次 `&nbsp;` 不受影响。
